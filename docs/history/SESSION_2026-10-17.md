## Goal #1 — image-source copies for the guest `3d5ebf4e` memcpy

**The claim to attack.** The guest compute shader `3d5ebf4e` is a dword memcpy of render-target
memory (1080p depth ~12 MB, a G-buffer target, two 960×540 targets), 8 dispatches per frame, and each
one currently goes image → download → buffer → upload → the shader. If a copy whose *source range is a
registered image* emitted an image copy instead (`vkCmdCopyImageToBuffer`, or a proxy-sized copy when
the scene is reduced — the source is often read back only to be sampled later as R32F), most of that
work disappears.

**Why the Deck is where it pays.** On the 7800 XT it is 0.5 ms of an 8.8 ms frame — and that GPU was
idle 2.1 ms of it, i.e. CPU-bound, so a GPU saving partly hides there. The work is memory-bound with
8 CUs and unified LPDDR5 on Van Gogh, against a 25–33 ms frame at 720p: best guess ≈10–20%, an
extrapolation in both directions. **Cheap to falsify** — the labels are already in `BB_GPU_PROFILE`.

**Verified open** (re-check before writing code): no buffer-copy path tests whether its source is an
image; `copyImageToBuffer` exists only for the upscaler and the memory model; `3d5ebf4e` is in no
source file and no game profile (`gpu/games/bloodborne.cpp` knows only
`buffer_copy_shader = 0xfefebf9f`).

## Plan

1. Read the copy path end to end — `vk_shader_hle.cpp` first, then the buffer-cache download/upload
   around `buffer_cache.cpp:807-936` and whatever resolves the source buffers in the HLE path.
2. Answer the one question that decides the design: **at the point the regions are built, is the
   source a `VideoCore::Buffer`, a registered image, or already a staging copy?** The image
   registration lives in the texture cache; if the HLE path never sees an image, the shortcut has to
   be installed where the ranges are made, or the download has to be recognised earlier.
3. Prototype behind a toggle (add one next to `MultiCopyShader`), guarded by the game profile so
   nothing changes for other titles.
4. Build on the Ubuntu server — the tree has never been built; `native_probe`/`build.sh` first to
   confirm the baseline compiles, then `out/gpu/libbbgpu.so`.
5. Measure with `BB_GPU_PROFILE=1` before/after on the same route: the copy shader's label, GPU idle,
   and the frame time. Then on the Deck, where the ordering (not the magnitude) is what the desktop
   numbers justify.

## Risks and open questions

- The source is often read back only to be sampled later as R32F: if that is true of all 8
  dispatches, an image→buffer copy may be the minimum, and the win is in *not* uploading again.
- Render-target layout and hazards: the destination upload is what keeps the mirror coherent; a
  shortcut that skips it can corrupt the frame rather than slow it.
- The 2.1 ms "GPU idle between submissions" is CPU-side; do not count it as this goal's gain twice.
- Every figure in `OPTIMIZATION_GOALS.md` is desktop-measured or extrapolated, and the taskset stand-in
  (4c/8t) is not a Deck.
