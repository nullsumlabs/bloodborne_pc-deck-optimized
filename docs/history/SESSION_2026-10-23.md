# 2026-10-23: the occlusion build's first Deck run — what the logs say, and the crash they found

The Deck run of `dist/Bloodborne-bbport-0.6-znver2-occlusion.AppImage` never reached gameplay: it
died on the load from the title screen, twice. The logs are in `~/bbwork/logs/bb-occlusion-tests/`
(`20261022_184533.{log,frames.csv,readbacks.csv}`, and the older `crash-20261019_024359.txt` from
the 2026-10-18 build).

## What the run measured

- 1560 logged frames over 26.5 s, all before the load: **median 16.67 ms** (60 FPS against the
  60 Hz vblank), p99 28.2 ms, six frames over 40 ms (the slowest 178.9 ms, during start-up).
  Nothing here says anything about gameplay.
- The title screen is not CPU-bound at all: `stage B busy 2.2%`, `GPU thread 25.6 µs/draw` at 14
  draws a frame, idle 95%, `Guest sleeps per frame: 6.5, 99.6 ms` (the game waiting for the
  flipper). §3/§5/§6/§7 cannot raise FPS from this state; only GPU work can, and no GPU time was
  recorded (`BB_GPU_PROFILE` was off).
- **The occlusion queries were never priced.** The only occlusion output in the log is the
  constructor's mode line (`occlusion results before the labels the game reads only`), printed at
  log line 485 — the run died at line 514, before the first five-second `Occlusion queries:` line.
  So this run is evidence for nothing in §4 except that the path was reached.
- The load itself is the one large number in the log: a **397.9 ms** frame with 586 draws, 119
  dispatches, 82 submissions, 304 images / 74 MB registered, **5304 GPU-thread page faults**, and
  **352.9 ms of GPU-thread user time** — 0.60 ms per draw, 23× the 25.6 µs/draw of a title frame.
  Then 342.3 ms and 47.7 ms, then the crash. `Buffer bindings: 444.7 MB/frame in place` in that
  window (0.8 MB in a steady title frame). Nobody has priced where those 352.9 ms go.

## The crash

```
Guest fault (signal 11) at guest offset 0x26d3c02, address 0x103b740018
  thread GXWorker:3; calls: +0x26af275 +0x1073060 +0x26d2402 ...
  thread GXWorker:1; calls: +0x26af275 +0x1073060 +0x26d2402 ...
  thread bb-probe;   calls: +0x26af275 +0x1075dd0 +0x26b4f3d ...
```

One RIP, one address, **three threads**, at the first load after the occlusion queries went live.
`0x103b740018` is inside the 152 MiB direct-memory mapping (`0x1039400000` + 152 MiB from the
log's own map lines), i.e. a page the game may write, and the fault line carried no register dump
(this tree builds without the crash recorder), so the kernel's error code was not visible.

**The leading cause: the label trap of `53c000d`, armed on a page the game writes itself.**
`WriteBeforeLabel` arms `WriteTraps::QueryReads` (reason 16 ⇒ `trap_level` 2 ⇒ **`PROT_NONE`**) on
the page holding a label the first time an event is pending. Label memory is the game's
small-object pool (`bbport_free_check.h`: 4 KiB pages, 48-byte label blocks), which the GXWorker
threads write every frame — so when the trap goes on, every thread that touches that page faults,
and the first fault handler lifts the trap for all of them. `OcclusionQueries::OnAccess` treated
the later faults as "not mine" and returned false, which `probe.c` turns into a fatal guest fault.
Several threads arriving on one freshly trapped page at once is what a label-page trap produces,
and three threads at one address is what the log shows. It also explains the timing: the queries
went live within a second of the death (the constructor's line and the fault are ~30 log lines
apart, across a 397.9 ms and a 342.3 ms frame).

**Fix (this session).** `OnAccess` now retries the instruction when the page's trap is gone but the
mapping still allows the access (`StaleLabelTrapFault`, `gpu/render/vk_occlusion_labels.h`); only a
page that is unmapped or still forbids the access stays a guest fault. The five-second
`Occlusion queries:` line gained `faults on an already lifted label trap: N`, so the next run says
whether this was it. The fatal guest-fault line now prints the kernel's `err` code and the page's
trap reasons (`src/probe.c`), which separates a wild pointer (`err 0x4`, `traps 0x0`) from one of
the port's own pages.

**The build itself.** `dist/Bloodborne-bbport-0.6-znver2-occlusion.AppImage` was rebuilt from this
fix (2026-10-23, `packaging/appimage.sh` over the znver2 `out/`; the packaged
`bb-probe` / `libbbgpu.so` / `libbbnet20.so` carry the same `.text` as those binaries). The
crashing package is kept as `dist/old/Bloodborne-bbport-0.6-znver2-occlusion-crashed.AppImage`, and
`dist/Bloodborne-bbport-0.6-znver2.AppImage` is left as the pre-§4 baseline for the A/B.

## The second run: 8.7 minutes of gameplay, no crash

Two real Deck runs of the rebuilt package (`~/bbwork/logs/bb-occlusion-tests-run2`): a 60 s
load-and-look run (`20261023_054107`) and an 8.7-minute run (`20261023_060517`, 28,281 frames,
520.6 s). **Neither crashed; 0 `Guest fault` lines in either log.** The fix's counter says why:
`faults on an already lifted label trap` = **10 in the first 60 s** (the load, exactly where the
2026-10-22 run died) and **3** across the long run. The race is real, frequent at a load, and now
retried instead of fatal — the diagnosis in the section above holds.

Frame times: **mean 18.41 ms (54.3 FPS), p50 17.95, p95 24.89, p99 28.30 ms**; 48–58 FPS in the
game windows. The 60 FPS stretch at the end (510–520 s) is a boss arena with water to the horizon
and no geometry — 59.7 FPS, GPU thread idle 65–72% at ~350 draws a frame — so it is not a speed
difference. stage A 7.8 ms a frame against an 18.4 ms frame, GPU thread ~10% idle in the heavy
windows: the frame is GPU-bound, so §3/§5/§6/§7 cannot raise FPS from it.

**§4's label half bought much less than it was built for** (details in `OPTIMIZATION_GOALS.md` §4):
2,761 of the 14,295 in-pass labels the game got while an event was pending were left to the next
boundary — 19%, ~0.1 pass break a frame, well under 0.1 ms. The game touches a label page within a
frame of a label landing there (~2,800 distinct pages read over the run, never more than 24 being
watched), so "learn each page once" converges almost everywhere. The order-it-anyway and
order-nothing modes bracket it; neither is worth another run.

**What is still unpriced is the queries themselves.** 101,602 of 126,378 counter reads returned
nothing, so the culling is real; `BB_OCCLUSION_QUERIES=0` at the same spot is the one A/B left.
Counter reuse before a result was written: 0 of 252,755, so predication was never fed a stale
counter in this run.

**The two 0-byte `readbacks.csv` files are not lost data.** That log gets a row only when a CPU
read of GPU-written memory has to download it, and in these runs none did: `Frame stats` reads
`0.0 blocks/s copied back` and layer memory `GPU data copied back 0 MiB` — the in-place model
serves those reads where the data already is (`readbacks/s` there counts the reads, not the
downloads). The port also ends with `std::_Exit(0)` (window closed), which does not flush stdio, so
with no row there was nothing to flush and the file stayed empty, header included. The header is now
flushed when the logger opens: an empty run leaves a header-only file instead of an
indistinguishable 0-byte one.

**Default flipped the same day.** With the label half at ≤0.1 ms and its only price being traps in
the game's own label pool, `LabelPolls::ModeFromEnv` now returns `Every` unless
`BB_OCCLUSION_LABEL_ORDER=2`: the shipped build orders before every label as the PS4 does and arms
no traps at all, and the narrow mode stays in the tree as the first entry of a planned *Experimental*
page in the launcher (`OPTIMIZATION_GOALS.md`). `occlusion-labels-test` covers the new default and
`=2`, and passes.

## Still open

- The queries' price: `BB_OCCLUSION_QUERIES=0` on Deck, same spot, `frames.csv` p50/p99 and
  `BB_GPU_PROFILE` GPU ms. The label half of §4 needs nothing more.
- The lighting popping on single items is still unattributed: §1 (empty-target draw skip) and the
  predication in `cp_graphics.cpp` are both candidates, and come out with `0 0` in
  `BB_TOGGLE_FILE` / `BB_OCCLUSION_QUERIES=0` respectively.
- The 397.9 ms load frame. Measure before changing anything: `BB_SECTIONS=1 BB_FRAME_STATS=1`
  (`stage B us per packet`, `stage A waits over 0.5%`), `BB_GPU_PROFILE=1` for GPU ms per pass,
  and the `Draw preparation: ... not ready` split. 0.6 ms of GPU-thread CPU per draw at a load is
  the largest CPU number anyone has recorded on this port, and it is a load/hitch item, not an
  FPS one.
