# Session 2026-10-20 — the first crash from the flightrec build, and why the log had no fault

A player sent the log from the `crash-logger-build` AppImage (2026-10-19, 05:56): 5000 lines, one
file, ending in `— the game exited (code 139) —`. The crash itself was not in it. This note is what
the log did say, how the missing part was diagnosed, and the two changes that make the next one
arrive complete.

## What the exported file is

The launcher's log page keeps the last `MAX_LOG_LINES` (5000) lines and *Экспорт журнала* writes
exactly that text, so the flush on disk is a console tail: 220 five-second frame-stat blocks,
~18 minutes, no start-up header (the `Crash report: <path>` line printed by `run.sh` had long
scrolled out). The recorder's report is a **separate file** that the button did not include, which
is why a crash arrived with no fault, no registers and no ring.

## What it showed

- Healthy to the last block: 48.0–48.8 FPS at 873–875 draws/frame, GPU thread ~13.0 µs/draw,
  idle ~30%, p50 20.5 ms, p99 25.6–28.4 ms.
- ~80 s before the end, an area change: 875 → 975 → 522 draws/frame, GPU idle 30% → 58%, p50
  21.3 → 20.0 ms, p99 24.9 → 22.0 ms; the guest GPU range allocator goes from 418 live/53.3 MB to
  205 live/111 MB (fewer, larger ranges).
- 20 s before the end: `Runtime: save data 'SPRJ0005' mounted at /savedata0 (existing)`.
- Then a normal 5 s block (50.0 FPS, p99 22.04 ms) and death inside the next one, silently: no
  stall line, no pipeline compile, no refusal, nothing on stderr.
- The recorder has no visible cost in this session: `0 recorder syncs` in all 220 blocks and p99 in
  the same 22–28 ms band throughout, including the four early 40–70 ms stalls at area loads. That
  is an observation, not the A/B in `OPTIMIZATION_GOALS.md` §11 (no `frames.csv`, no off run).

## The deduction that found the report

`139` in the launcher is not "killed by SIGSEGV": GLib reports a signal death as `-1` (checked here
with a real `SIGSEGV` child through `Gio.Subprocess`: `get_if_exited()` false, printed status `-1`).
`139` is `WEXITSTATUS`, i.e. `_exit(128 + 11)` — the port's own handler. And `run.sh` `exec`s
`bb-probe`, so no shell rewrites the status. If `runtime_crash_begin` had failed to open its file it
would have fallen back to stderr and dumped the whole report into the log; stderr is empty. So the
handler ran, the file was opened, and the report is sitting in `<data>/logs/crash-<start>.txt`
(`~/.local/share/bbport/logs` for the AppImage), unwritten into what was sent.

## Changes

- `src/runtime_crash.c`: when the report goes to a file, `runtime_crash_begin` also writes two lines
  to stderr — the path and the fault line. The console log, and any export of it, then names the
  report and where the game died, instead of ending in a bare exit status.
- `launcher/bbport_launcher.py`: *Экспорт журнала* appends the `crash-*.txt` written since this
  run's start (under `===== <path> =====`), so one file holds both the console tail and the black
  box. A report older than the run is never appended; a session that did not crash exports the log
  alone.
- `tests/test_crash.c`: the crashing child's stderr is captured and must hold the path and the
  fault line and *not* the report itself (the old writer fails this, the new one passes).
- `docs/CRASH_RECORDER_PLAN.md`: "Where a crash leaves its evidence" — the file, the two stderr
  lines, and what `139` versus `-1` means.

## The report arrived

The player sent `<data>/logs/crash-20261019_024359.txt` that evening: 10,039 lines, 895 KB. The
name carries the *start* of the session, 02:44:07 — `run.sh` stamps it before the game runs — and
the fault is 3 h 12 m later at 05:56:34; the export `bbport-20261019_055650.log` was made 16 s
after it, so the two files are one event. (A start-stamped name is why the report is easy to miss.)
Build `Oct 18 2026 09:44:17`, `BB_PC_MODEL=1`, `BB_GUEST_IN_PLACE=1`, `BB_DMEM_MB=9152`,
`BB_FRAME_STATS=1`, `BB_WRITE_LOG` unset.

### The fault

```
FAULT signal=11 (SIGSEGV) address=0x4 tid=3564        ; thread HavokWorkerThre
  Guest fault (signal 11) at guest offset 0x263b8e7, address 0x4
  ... r14=0000000000000004, rax=0000001041401fc0, rbx=00000010282a2060 ...
```

`0x263b8e7` is the free-list pop this branch has been chasing since 2026-09-30 — *not* the null
store of 2026-10-17 (`0x2199310`). The disassembly (`eboot/dumps/fault-0x263b8e7.dis`, from
`eboot.py dis 0x263b8e7`) shows why the address is `0x4`:

```
263b8b0: push rbp ...                          ; the game's 48-byte pool: allocate one block
263b8bd: mov  (%rbx),%rax                      ; rax = the page header with free blocks
263b8e3: mov  0x10(%rax),%r14                  ; r14 = header->head (the free list)
263b8e7: mov  (%r14),%rcx                      ; <-- fault: reads the link of the first free block
263b8ea: mov  %rcx,0x10(%rax)                  ; header->head = that link
```

`rax` = `0x1041401fc0` is `page 0x1041401000 + 0xfc0`, the header of one 4 KiB page of 48-byte
blocks (`HeaderOffset`/`BlockSize` in `gpu/shim/bbport_free_check.h`), so the pop was genuine and
`r14` = `header->head` = **4**: the free-list head itself held `4` where a block pointer belongs.
Either the header was written, or an earlier pop copied that `4` out of a free block's first qword,
which is the shape the fingerprint was recorded in before. `rbx`, the pool, is `0x10282a2060` — the
object whose live-range counters the frame stats print in all 220 blocks of the log
(`GPU range allocators: 0x10282a2060: 306 live, 120.4 MB`), so the block that lost its link is a
node of the GPU range allocator (48 bytes each).

### What `4` is

Not garbage, and not a pointer: it is the value the game's GPU-side fence writes when a range or a
label is **done**. `bbport_free_check.cpp` says so itself — the collector's done branch (`0x26aa986`)
reads a block's first dword and takes the block as done when it reads `4` — and `runtime_memory.c`
documents the same fingerprint from the memcpy fix: *"a free-list link ending in 0x00000004: guest
fault 0x263b8e7"*. `4` is what a 4-byte fence write leaves in a block that was handed back to the
pool in between. The historical corruption was `0x0000005300000000` (the same thing, 0x53 at
offset 4); this is the same race, arriving later and finding a range node.

That it was a worker thread that died is only who allocated next: the Havok worker took a node from
the allocator, and the allocator's first free block had a fence value where its link should be.

### What the session was doing

- **Not out of memory.** The memory section has 20 events, the last at `+6.819 s`, and nothing for
the following 3 h 11 m; the heap trend says `(no sample yet)` because `BB_CRASH_HEAP_SECONDS` was
unset, so neither number says anything about pressure — but nothing was asking for memory either,
and the 2026-10-17 question (was the allocation refused?) does not arise for this fault.
- `EOP fences: 239409889 decoded, 239409889 labels written, 0 pending` in the last window: nothing
was left pending when the counters printed, so the late write is inside the last seconds (or the
counters cannot see a write that was re-ordered rather than pending).
- ~80 s before the end an area change: 875 → 975 → 522 draws/frame, idle 30 % → 58 %, range
allocator 418 live/53.3 MB → 205 live/111 MB; 20 s before it, the save `SPRJ0005` was mounted.
Then one normal 5 s block and death. Streaming — the churn of ranges and label blocks this race
needs.

### What is not known, and the measurement that answers it

Which write landed in the freed block. The port has the instrument for exactly this
(`BB_FREE_CHECK=1`, `gpu/shim/bbport_free_check.cpp`), and it was **off**: the watcher prints a
heartbeat every 10 s and the 5000-line console tail has no `Free check:` line at all. With it on,
`Check()` reports the write *before it lands* — source (EOP, EOS, WriteData, DMA, download), value,
stream sequence, tid, and the block's alloc/free ages — and the watcher reports the corrupted list
as soon as it appears. `BB_LABEL_TRAP=2` adds the guest's own release call chain for a block freed
while its fence is pending.

The launcher's *Для разработчика → Диагностика вылетов* turns on `BB_FREE_CHECK` **together with**
`BB_WRITE_LOG=1`, which is the one thing that used to hide this race (2026-09-30: even nanoseconds
of delay on the label writes masked it). For this signature the free check alone is the right tool.
The crash report's header now records `BB_FREE_CHECK`, `BB_LABEL_TRAP`, `BB_DRAW_PIPE` and
`BB_PIPE_SIGNALS`, so the next report says whether they were on without digging in the log.

## Still open

- **Who wrote `4` into that block** — the one fact the report cannot carry; needs a run with
  `BB_FREE_CHECK=1` (no `BB_WRITE_LOG`) and, ideally, `BB_LABEL_TRAP=2`, from this build or later.
- The label/range race itself: the pipeline fix (2026-09-30) and the single-store fix (2026-10-06)
  removed the 7-of-7 case and most soak failures, but 3 h 12 m of play still found a path. The
  drained `sceGnmSubmitDone` and the deferred fences are the places to look once the writer is
  named.
- Neither change is in the flightrec AppImage (built 2026-10-18): it needs `build_steam_deck.sh` +
  `packaging/appimage-repack.sh` again, and then a real crash to prove the export path on the Deck.
