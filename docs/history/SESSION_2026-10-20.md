# Session 2026-10-20 — the first crash from the flightrec build, and why the log had no fault

A player sent the log from the `crash-logger-build` AppImage (2026-10-19, 05:56): 5000 lines, one
file, ending in `— the game exited (code 139) —`. The crash itself was not in it. This note is what
the log did say, how the missing part was diagnosed, and the two changes that make the next one
arrive complete.

## What the exported file is

The launcher's log page keeps the last `MAX_LOG_LINES` (5000) lines and *Экспорт журнала* writes
exactly that text, so the flush on disk is a console tail: 220 five-second frame-stat blocks,
~18 minutes, no start-up header (the `Crash report: <path>` line printed by `run.sh` had long
scrolled out). The recorder's report is a **separate file** that the button did not include, which
is why a crash arrived with no fault, no registers and no ring.

## What it showed

- Healthy to the last block: 48.0–48.8 FPS at 873–875 draws/frame, GPU thread ~13.0 µs/draw,
  idle ~30%, p50 20.5 ms, p99 25.6–28.4 ms.
- ~80 s before the end, an area change: 875 → 975 → 522 draws/frame, GPU idle 30% → 58%, p50
  21.3 → 20.0 ms, p99 24.9 → 22.0 ms; the guest GPU range allocator goes from 418 live/53.3 MB to
  205 live/111 MB (fewer, larger ranges).
- 20 s before the end: `Runtime: save data 'SPRJ0005' mounted at /savedata0 (existing)`.
- Then a normal 5 s block (50.0 FPS, p99 22.04 ms) and death inside the next one, silently: no
  stall line, no pipeline compile, no refusal, nothing on stderr.
- The recorder has no visible cost in this session: `0 recorder syncs` in all 220 blocks and p99 in
  the same 22–28 ms band throughout, including the four early 40–70 ms stalls at area loads. That
  is an observation, not the A/B in `OPTIMIZATION_GOALS.md` §11 (no `frames.csv`, no off run).

## The deduction that found the report

`139` in the launcher is not "killed by SIGSEGV": GLib reports a signal death as `-1` (checked here
with a real `SIGSEGV` child through `Gio.Subprocess`: `get_if_exited()` false, printed status `-1`).
`139` is `WEXITSTATUS`, i.e. `_exit(128 + 11)` — the port's own handler. And `run.sh` `exec`s
`bb-probe`, so no shell rewrites the status. If `runtime_crash_begin` had failed to open its file it
would have fallen back to stderr and dumped the whole report into the log; stderr is empty. So the
handler ran, the file was opened, and the report is sitting in `<data>/logs/crash-<start>.txt`
(`~/.local/share/bbport/logs` for the AppImage), unwritten into what was sent.

## Changes

- `src/runtime_crash.c`: when the report goes to a file, `runtime_crash_begin` also writes two lines
  to stderr — the path and the fault line. The console log, and any export of it, then names the
  report and where the game died, instead of ending in a bare exit status.
- `launcher/bbport_launcher.py`: *Экспорт журнала* appends the `crash-*.txt` written since this
  run's start (under `===== <path> =====`), so one file holds both the console tail and the black
  box. A report older than the run is never appended; a session that did not crash exports the log
  alone.
- `tests/test_crash.c`: the crashing child's stderr is captured and must hold the path and the
  fault line and *not* the report itself (the old writer fails this, the new one passes).
- `docs/CRASH_RECORDER_PLAN.md`: "Where a crash leaves its evidence" — the file, the two stderr
  lines, and what `139` versus `-1` means.
